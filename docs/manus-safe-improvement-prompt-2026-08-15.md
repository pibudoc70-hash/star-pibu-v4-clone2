## 작업 원칙

1. 먼저 **분석만** 수행하라. 파일을 수정·배포·GitHub push·환경변수 변경·DB 마이그레이션·의존성 대규모 업데이트를 하지 마라.
2. 현재 브랜치·커밋·작업 트리·최근 체크포인트를 확인하고, `pnpm check`, `pnpm lint`, `pnpm test`, `pnpm build`, `pnpm audit --audit-level moderate`, `git diff --check`를 실행하라.
3. 빌드가 SIGTERM으로 중단되면 즉시 코드 오류로 단정하지 말고, 메모리·감시 프로세스·브라우저 프로세스를 분리 진단한 뒤 한 번씩만 안전하게 재시도하라. 반복 실패 시 원인과 재현 조건을 보고하고 임의의 빌드 설정 완화는 하지 마라.
4. 실제 운영 도메인과 개발 미리보기에서 대표 한국어·영어·일본어·중국어 간체·중국어 번체 경로를 확인하라. URL, canonical, hreflang, SSR/프리렌더, 네비게이션, 외부 링크, 모바일 레이아웃을 회귀 검증한다.
5. 사용자가 승인한 단계만 한 번에 하나씩 구현한다. 각 단계는 **기준선 체크포인트 → 최소 수정 → 관련 단위 테스트 → 실제 화면 확인 → 전체 회귀 → 변경 범위 확인 → 체크포인트** 순서를 지켜라.
6. 체크포인트는 자동 배포될 수 있으므로, 사용자 승인이 없는 기능 변경을 저장·배포하지 마라. force push, `git reset --hard`, lint rule 비활성화, 광범위한 `eslint-disable`, `any` 추가를 금지한다.
7. 비밀값·토큰·쿠키·DATABASE_URL·개인정보를 출력하지 마라.
8. DB 기반 다국어 본문, 특히 중국어 번체 본문은 데이터 현지화 과제다. 누락된 번역을 코드 폴백·기계적 간체→번체 변환으로 감추지 마라.

## 1차 분석 보고서에서 반드시 제시할 개선 후보

아래 순서대로 각 후보를 조사하되, 현재 단계에서는 수정하지 마라. 항목마다 근거 파일·영향도·수정 범위·예약/OTP 비접촉 여부·테스트 방법·롤백 방법을 표로 정리하라.

### P1. 정적 분석과 테스트 품질

- lint 경고 185건을 유형별로 분류한다. 실제 품질·보안·유지보수성에 영향을 주는 경고와 테스트/레거시 노이즈를 구분한다.
- 오류 0을 유지하면서, 기능 단위로 안전하게 해소할 수 있는 경고만 우선순위화한다. eslint 설정을 완화하거나 무시 주석으로 덮지 마라.
- Vitest 환경이 브라우저 전용 코드와 서버 코드를 적절히 분리하는지 점검한다. 테스트가 파일명·문자열만 확인해 실제 사용자 흐름을 놓치는 구간을 식별한다.
- 외부 예약 URL 정책·다국어 CTA·새 창 보안 속성은 유지하고, 예약/OTP 대상 테스트에는 추가 변경을 제안하지 마라.

### P2. 프런트엔드 신뢰성·접근성

- 전역 ErrorBoundary, 라우트별 로딩·오류·빈 상태, 이미지 대체 텍스트, 버튼의 접근 가능한 이름, 키보드 포커스, 메뉴·모달의 ARIA 상태를 감사한다.
- 모바일 390px 기준으로 헤더, 상세 페이지 상단, 다국어 Directions, 외국인 안내, 이벤트/장비 카드에서 텍스트 잘림·가로 스크롤·대비 부족을 확인한다.
- 한글·영어·일본어·중국어 간체·중국어 번체의 i18n 키 누락과 접근성 라벨 불일치를 조사한다. 중국어 번체 DB 본문 번역 문제는 코드 수정으로 해결하려 하지 말고 데이터 백로그로 분리한다.

### P3. 성능과 번들 관리

- Vite production build의 큰 청크(예: 다이어그램·차트·관리자 코드·코드 하이라이팅 등)를 분석한다.
- 공개 진료 페이지의 LCP·CLS·INP에 영향을 주는 이미지, 폰트, 불필요한 초기 JavaScript, 과도한 lazy loading을 찾는다.
- 실제로 필요한 경로에만 안전한 dynamic import·route-level code splitting을 제안한다. SSR/프리렌더, canonical, FAQPage JSON-LD, 기존 URL·다국어 경로를 깨는 변경은 금지한다.
- 성능 개선은 Lighthouse 또는 동등한 재현 가능한 측정 전후값이 확보되는 경우에만 제안한다.

### P4. SEO·AI 크롤러·콘텐츠 전달 정합성

- 홈·시술·장비·공지·연구·의료진·Directions·다국어 대표 경로의 canonical, hreflang(ko/en/ja/zh-CN/zh-TW/x-default), og:locale:alternate, sitemap, robots.txt를 표본 감사한다.
- 서버 프리렌더 원본 HTML에 본문·FAQ·FAQPage·MedicalClinic·Physician·MedicalProcedure·Article JSON-LD가 실제로 포함되는지 점검한다.
- 구조화 데이터의 기관명·주소·전화·진료시간·의료진 정보(NAP)와 화면 텍스트의 불일치를 발견하면 근거와 정확한 데이터 원본을 보고한다. 의료 광고상 보증·최상급·타 병원 비교 문구를 새로 넣지 마라.

### P5. 서버 보안·운영 신뢰성

- 인증·권한·관리자 역할 보호, healthz 외부 노출, 오류 로그 개인정보 마스킹, storage key/URL 검증, 공개 파일 제공, CSP/보안 헤더를 **읽기 전용**으로 다시 감사한다.
- OAuth state, 세션 만료, SameSite, CSP는 설계 변경으로 이어질 수 있으므로 문서·SDK 근거가 없는 한 수정 제안만 하고 구현하지 마라.
- `healthz`는 외부에 최소 상태만 노출하고 실제 오류·SQL·호스트·stack trace를 포함하지 않는지 확인한다.

### P6. 유지보수성·배포 위생

- 반복된 상수, 죽은 코드, 사용하지 않는 import, 중복 i18n 값, 오래된 주석을 찾되, 공개 UI·URL·스타일을 바꾸지 않는 최소 정리만 후보로 제시한다.
- `todo.md`, 검증 문서, CI 스크립트와 실제 코드 상태의 불일치를 확인한다.
- 의존성은 audit 결과와 운영 영향도를 기준으로만 제안한다. lockfile 전체 교체나 메이저 버전 일괄 업그레이드는 별도 승인 없이는 금지한다.

## 1차 분석 보고서 형식

아래 형식을 반드시 지켜라.

1. 현재 브랜치, 커밋, 작업 트리, 마지막 체크포인트
2. 타입 검사, lint, 테스트, build, audit 결과를 다음 분류로 표기: 통과 / 실제 코드 오류 / 기존 warning / 환경 제약 / 예약·OTP 제외 대상
3. P1~P6 개선 후보 우선순위 표
   - ID, 문제, 근거 파일·화면, 사용자 영향, 위험도, 예상 수정 파일, 예약·OTP 비접촉 확인, 검증 방법, 롤백 지점
4. **즉시 수정 권장**: 작고 되돌리기 쉬우며 공개 기능 회귀 가능성이 낮은 항목만 최대 3개
5. **승인 필요**: UI/콘텐츠/SEO/보안 정책/DB/의존성/배포에 영향을 주는 항목
6. **명시적 제외**: 예약·OTP·외부 예약 링크, 중국어 번체 DB 본문 현지화, 사용자 승인 없는 디자인 변경
7. 다음 단계에서 실행할 작업을 한 단계만 제시하고 사용자 승인을 기다린다.

## 사용자 승인 후 구현 규칙

- 한 단계에서 하나의 목적만 수행한다. 코드 리팩터링과 디자인 변경, 보안 정책 변경, 데이터 마이그레이션을 섞지 마라.
- 수정 전에 정확한 파일·행위·테스트 계약을 읽고, 수정 직후 해당 단위 테스트를 먼저 실행한다.
- 그 뒤 `pnpm check`, `pnpm lint`, 관련 테스트, 전체 `pnpm test`, `pnpm build`, `git diff --check`, 대표 실제 화면 확인을 수행한다.
- build 실패가 환경 메모리 문제인지 코드 오류인지 분리해 보고한다. 코드 오류가 아니면 임의로 비기능 설정을 변경하지 않는다.
- 보호 대상 파일이 변경 목록에 나타나면 즉시 중단하고, 해당 파일 변경을 되돌린 뒤 사용자에게 보고한다.
- 각 단계 완료 후 변경 파일, 검증 결과, 남은 위험, 예약·OTP 비변경 확인을 간결히 보고하고, 사용자 승인 후에만 다음 단계로 진행한다.

## 사용 방법

이 프롬프트는 **먼저 읽기 전용 감사와 우선순위 보고서만 받는 용도**입니다. 분석 결과에서 최대 세 개의 저위험 개선안을 받은 뒤, 원하는 항목의 ID를 골라 별도로 구현 승인하면 됩니다. 이 방식은 기능·디자인·다국어 URL을 불필요하게 변경하지 않으면서도 테스트와 실제 화면 검증을 단계별로 요구합니다.
