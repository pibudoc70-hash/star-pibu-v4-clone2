## STEP 3 운영 확인

Pretendard 웹 서브셋 배포 후 두 파일은 스토리지 리다이렉트 목적지에서 모두 `200`, `Content-Type: font/woff2`, 장기 캐시 헤더로 확인되었다. Latin·공통 기호 파일은 91,572B, 한국어 파일은 548,764B이며, 기존 2,057,688B 단일 파일 대비 첫 방문 전송 후보가 크게 줄었다. 브라우저 자동화 환경이 반복적으로 종료되어 화면 수준의 글리프 probe는 이 단계에서 재현하지 못했으나, CSS `unicode-range`와 파일 MIME·HTTP 응답·정적 회귀 테스트로 검증 범위를 제한했다.

## STEP 4 — 히어로 캔버스

**이번 배포에서는 적용하지 않았다.** `HeroStarfield.tsx`에는 별·성운 캔버스의 60fps 루프가 남아 있지만, 현재 `client/src`에서 해당 컴포넌트를 import·렌더하는 위치가 없다. 따라서 별 개수·DPR·visibility 변경은 실제 방문자 성능을 개선하지 않으며, 동작하지 않는 코드에 복잡도를 추가하는 것은 합리적이지 않다. 향후 이 효과를 다시 연결하기로 결정될 때에만 reduced-motion, visibility pause, DPR 상한 및 30fps 프레임 제한을 별도 설계·검증한다.

## STEP 5 — 다국어 청크

**보류한다.** 현재 `LangProvider`는 `i18n.ko/en/ja/zh/zh-TW`를 동기적으로 조립하고, 렌더 트리 전체에 즉시 `t`를 제공한다. 이를 동적 import로 바꾸려면 언어 판정·데이터 로딩·Suspense/fallback·문서 언어 갱신을 함께 재설계해야 한다. 경로별 SEO·첫 렌더 일관성·다국어 페이지의 hydration 안정성에 영향을 줄 수 있으므로, 충분한 번들 분석과 locale 전환 회귀 설계 없이는 적용하지 않는다.

## STEP 6 — CSS 분리

**보류한다.** `index.css`는 엔트리에서 동기 import되며 Hero도 홈 초기 렌더 경로에 동기 포함된다. Hero 규칙만 별도 CSS로 옮겨도 초기 홈에서 즉시 다시 로드되어 전송량 절감이 없고, 전역 cascade·키프레임·반응형 규칙이 흩어진 현재 구조에서는 시각 회귀 위험이 높다. 먼저 Chrome Coverage로 실제 미사용 구간을 정량화한 뒤, 독립 cascade layer 단위로 분리해야 한다.

## STEP 7 — 준정적 API 캐시

**추가 서버 캐시는 적용하지 않는다.** React Query는 이미 브라우저 메모리에서 5분 `staleTime`, 포커스 재요청 비활성화, 1회 재시도를 사용한다. 반면 이벤트·공지·상담 구성은 관리자 변경의 최신성이 중요하며, 공용 서버 캐시는 endpoint별 무효화와 인증·권한 경계를 함께 설계해야 한다. 이러한 무효화 설계 없이 5~10분 서버 캐시를 추가하면 노출 내용·가격·운영 정보가 오래 남을 위험이 있다.

## 후속 권장 순서

1. 운영 환경의 브라우저 자동화 안정화 후 STEP 3의 5개 locale 화면 글리프·FOIT/FOUT를 재측정한다.
2. Coverage 결과로 홈 초기 CSS의 실제 미사용 비율이 충분히 클 때에만 STEP 6을 독립 작업으로 설계한다.
3. 다국어 청크는 동기 `LangProvider`를 유지하는 상태에서 번들 기여도를 먼저 수치화한 뒤, 별도 승인 후 진행한다.
